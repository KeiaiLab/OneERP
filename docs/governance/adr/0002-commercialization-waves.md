# ADR-0002: 모듈 상용화 웨이브 순서 정책

## 메타데이터

| 필드 | 값 |
|------|----|
| 상태 | Accepted |
| 채택일 | 2026-04-13 |
| 결정권자 | OneERP 아키텍처 위원회, 제품 위원회 |
| 영향 범위 | `services/`, `apps/web/`, 모든 도메인 모듈 |
| 관련 ADR | ADR-0001(상용 정의), ADR-0011(런타임 plane), ADR-0012(웨이브 명세) |
| 후속 phase | M-1.x (Wave 1), M-2.x, M-3.x, M-4.x 마일스톤 |

## 1. 맥락(Context)

ADR-0001이 "상용 제품 = 23개 게이트 통과"로 정의했다. `docs/generated/INDEX.md`
기준 모듈은 47개이며, 모든 모듈을 동시에 상용화하는 것은 인력·예산·
리스크 측면에서 불가능하다. 동시 진행은 다음 문제를 만든다:

- **인지 부하**: 47개 모듈을 동시에 상용화 게이트 23개에 맞추면
  컨텍스트 스위칭으로 평균 작업 효율이 급감한다.
- **인프라 자원**: SLO 측정·부하 시험·Chaos 테스트는 환경을 점유한다.
  47개 동시 진행 시 환경 충돌 빈발.
- **고객 가치 시점**: 모든 모듈이 동시에 80% 완성보다, 핵심 모듈이
  먼저 100%인 것이 외부 도입 검토에 유리하다.
- **회귀 리스크**: 동시 변경 모듈이 많을수록 cross-module 회귀 추적이
  어려워진다.

또한 ERP 도메인은 모듈 간 의존성이 강하다(예: 모든 거래는 회계 전표
생성, 모든 직원 거래는 HR Employee 참조). 의존받는 모듈이 먼저
상용화되지 않으면 의존하는 모듈이 상용화 게이트를 통과할 수 없다.

근거 인벤토리:
- `docs/generated/INDEX.md` — 47 모듈 목록
- `docs/engineering/data/er-entities.md` — 엔티티 의존 그래프
- `docs/engineering/architecture/be-context-map.md` — 컨텍스트 경계
- `docs/product/scope/03-e2e-scenarios.md` — 5대 E2E 시나리오 (판매·구매·재고·회계·권한)

## 2. 결정(Decision)

OneERP는 47개 모듈을 **4개 웨이브(Wave 1~4)** 로 분류하고, 다음 규칙에
따라 순차 상용화한다:

- **단일 진행 웨이브**: 한 시점에 "**활성 웨이브**"는 1개만 둔다.
  활성 웨이브의 모든 모듈이 `pre-commercial` 라벨에 도달한 뒤에야
  다음 웨이브를 활성화한다.
- **웨이브 내 병렬 허용**: 활성 웨이브 안에서는 모듈별 phase를
  병렬로 진행할 수 있다(인프라 안전장치가 충족된 한).
- **선결 의존성**: 어떤 모듈도 자신의 의존 모듈이 적어도 `beta`
  라벨에 도달하지 않으면 게이트 G1-3(통합 테스트) 이후 작업을
  시작할 수 없다.
- **분류 기준**: §6의 4축 점수표(매출 영향, 의존도, 리스크, 사용 빈도)
  로 모듈별 점수를 산출하여 웨이브를 결정한다.
- **재분류**: 분기 회고에서 점수 변화가 임계값(±5점)을 넘으면 본 ADR을
  supersede하는 새 ADR로 웨이브 분류를 갱신한다. 본 ADR 자체는 불변.

웨이브 구체 명세(어떤 모듈이 어디 속하는지 + 진입/완료 조건)는
**ADR-0012**로 분리한다. 본 ADR은 분류 **방법론**만 정의한다.

- **범위 In**: 47개 ERD 모듈, BE 서비스, FE 모듈.
- **범위 Out**: 인프라 baseline(ADR-0008~0010이 별도 결정),
  플랫폼 기반(ADR-0004~0007), 신규 모듈(ADR-0012 후속 ADR로 확장).
- **발효 시점**: ADR-0012 채택과 함께 발효.

## 3. 대안(Alternatives Considered)

### 대안 A — 모든 모듈 동시 상용화
- 설명: 47개 모듈을 균등 진행.
- 장점: 모든 영역이 균일하게 진보.
- 단점: 위 §1의 4가지 문제 모두 발생. 상용 라벨 도달 시점이 무한정
  뒤로 밀린다.
- 채택하지 않은 이유: 자원·인지 한계.

### 대안 B — 모듈 단위 단일 진행 (1개씩)
- 설명: 한 번에 1개 모듈만 상용화.
- 장점: 컨텍스트 집중 최대화.
- 단점: 47개를 직렬로 처리 시 시점 지연 과다. 의존 관계상 cross-module
  변경이 빈번해 단일 모듈 격리가 비현실적.
- 채택하지 않은 이유: 시점 비용이 가치 손실 초과.

### 대안 C — 가치 기반 우선순위만 사용 (의존 무시)
- 설명: 매출 영향이 큰 모듈부터.
- 장점: 단순.
- 단점: 의존 모듈 미준비 시 통합 테스트 불가, 회계가 미준비된 상태에서
  판매 모듈 상용화 시도 시 G1-3 게이트 통과 불가.
- 채택하지 않은 이유: 의존성을 무시하면 게이트가 깨진다.

### 대안 D — Strangler Fig 방식 (외곽부터)
- 설명: 외부 인터페이스 모듈부터 상용화.
- 장점: 기존 시스템과 점진적 교체 가능.
- 단점: OneERP는 신규 시스템이므로 strangler 적용 대상 외부 시스템이
  없음.
- 채택하지 않은 이유: 컨텍스트 부적합.

### 대안 E — 현 상태 유지 (Do Nothing)
- 비용: 모듈 우선순위 즉흥 결정 지속, 매 분기 협상 비용.
- 리스크: 정치적 결정으로 의존성 위반.
- 채택하지 않은 이유: 본 ADR이 정의하는 객관 점수표가 즉흥 결정의
  일관성 비용을 줄인다.

## 4. 근거(Rationale)

| 평가 축 | 점수 | 비고 |
|---------|------|------|
| 비용 | 4/5 | 점수 산출은 1회성, 운영 부담 낮음 |
| 리스크 | 5/5 | 의존 위반 차단으로 게이트 실패 사전 방지 |
| 운영 | 4/5 | 활성 웨이브 단일화로 자원 충돌 최소화 |
| 팀 역량 | 4/5 | 점수표가 토론 프레임을 제공 |

- **결정적 근거**: 의존성 위반 차단(G1-3, G3-3 게이트 통과 가능성
  보장)과 자원 충돌 최소화.
- **수용한 트레이드오프**: 후순위 모듈은 상용화 시점이 늦어진다.
  반대급부로 선순위 모듈은 안정적 의존 기반 위에서 상용화된다.

## 5. 영향(Consequences)

### 5.1 긍정적 영향
- 모듈별 상용화 일정 예측 가능.
- 의존 깨짐으로 인한 게이트 실패 사전 방지.
- 외부 도입 시 "Wave 1 모듈은 SLA 약속 가능" 형태의 단계적 마케팅 가능.
- 회고 시 점수 변화 추적으로 우선순위 변화 객관화.

### 5.2 부정적 영향 / 리스크
- 후순위 모듈 오너의 사기·자원 확보 어려움.
- 점수 산출이 정치화될 위험 → §6의 점수표를 공개·문서화로 완화.
- "활성 웨이브 단일화" 원칙이 긴급 작업(보안 패치 등)을 방해할 수 있음
  → §7의 예외 조항 참조.

### 5.3 마이그레이션 / 호환성
- 본 ADR은 분류 방법만 정의하므로 코드 영향 없음.
- 기존 진행 중 작업은 ADR-0012의 웨이브 매핑에 따라 활성/대기 분류.

### 5.4 측정 지표

| 지표 | 현재 | 목표(6개월) | 측정 |
|------|------|-------------|------|
| 활성 웨이브 모듈 평균 라벨 | n/a | `pre-commercial` 이상 | `commercial-status.md` |
| 웨이브 외 작업 비중 | n/a | < 20% | git log per phase |

## 6. 분류 점수표 (4축 100점 만점)

각 모듈에 대해 다음 4축에서 점수를 산출한다.

### 6.1 축 1 — 매출/계약 영향 (0~30점)

| 기준 | 점수 |
|------|------|
| 모듈 미보유 시 계약 자체 불가 (ERP 핵심: 회계, HR, 판매, 구매, 재고) | 30 |
| 모듈 미보유 시 일부 산업 계약 불가 (제조, POS, 프로젝트, 자산) | 22 |
| 보조 모듈 (CRM, 문서, 캘린더) | 14 |
| 차별화 모듈 (분석, BI, RPA, IoT) | 10 |
| 기타 (위키, 게시판, 메일) | 5 |

### 6.2 축 2 — 의존도(in-degree) (0~30점)

`docs/engineering/data/er-entities.md`의 외래 참조 그래프 기준,
**나에게 의존하는 모듈 수**.

| 의존받는 모듈 수 | 점수 |
|------------------|------|
| 10개 이상 (회계, HR, Directory) | 30 |
| 5~9개 (재고, 판매, 구매) | 22 |
| 2~4개 | 14 |
| 1개 | 7 |
| 0개 (말단 모듈) | 0 |

### 6.3 축 3 — 운영 리스크 (0~20점)

| 기준 | 점수 |
|------|------|
| 데이터 손상 시 법적/재정 영향 (회계, 급여, 컴플라이언스) | 20 |
| 가용성 중단 시 일상 업무 마비 (인증, 게이트웨이) | 18 |
| 데이터 손상 시 운영 영향 큼 (재고, 자산) | 14 |
| 통상 운영 영향 | 8 |
| 비핵심 (말단) | 3 |

### 6.4 축 4 — 사용 빈도 (0~20점)

| 기준 | 점수 |
|------|------|
| 일 사용자 80% 이상 (메인 화면, 알림, 검색) | 20 |
| 주 단위 핵심 (전표, 휴가, 결재) | 16 |
| 월 단위 핵심 (마감, 급여) | 10 |
| 분기/연 단위 (감사, 평가) | 5 |
| 비정기 | 2 |

### 6.5 웨이브 매핑

| 점수 합 | 웨이브 |
|---------|--------|
| 80~100 | Wave 1 (재무·운영 핵심) |
| 60~79 | Wave 2 (운영 확장) |
| 40~59 | Wave 3 (지원·전문 영역) |
| 0~39 | Wave 4 (협업·확장 영역) |

같은 점수 구간에서 분류 위치가 모호하면 의존도 축이 우선한다
(의존받는 쪽이 먼저 안정화돼야 한다).

## 7. 예외 조항

다음 경우 활성 웨이브 단일화 원칙의 **임시 예외**를 허용한다.
예외 발동 시 phase 메모에 사유와 종료 시점을 기록한다.

- **보안 사고/취약점**: CVSS 7.0 이상 발견 시 모든 영향 모듈에서 즉시
  대응(웨이브 무관).
- **데이터 정합성 사고**: 운영 데이터 손상 발견 시 영향 모듈 즉시 수정.
- **법규 변경 deadline**: 외부 법규 발효일 N일 이내 시 해당 모듈 우선.
- **활성 웨이브 의존 차단**: 활성 웨이브 모듈이 후순위 모듈에 막혀
  `beta` 이상 도달 불가능할 경우, 막는 모듈을 임시 활성화.

예외는 분기당 3건을 초과할 수 없다(원칙 자체의 무력화 방지).
