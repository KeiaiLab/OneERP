# OneERP 아키텍처 우선 전체 리팩토링 설계서

## 1. 배경

OneERP는 `core`, `planes`, `services`, `web`, `deploy`, `scripts`가 함께 존재하는 모노레포다.
현재 저장소에는 `stack-smoke.sh`, `tests/e2e`, `tests/e2e-ui`, `web/tests/e2e` 등 검증 자산이 적지 않지만,
배포 직전 관점에서는 "부팅은 되지만 실제 사용자 흐름이 깨지는 문제"를 한 번의 정의로 막지 못하고 있다.

사용자 선택 기준은 다음과 같이 확정됐다.

- 전체 리팩토링은 한 번에 구현하는 작업이 아니라 단계적 마스터플랜으로 설계한다.
- 접근 방향은 `아키텍처 우선`으로 한다.
- 가장 먼저 줄여야 할 리스크는 `부팅은 되지만 실제 실행 흐름이 깨지는 상황`이다.
- 시간보다 신뢰성을 우선한다.

## 2. 가정과 제약

### 가정

- `ADR-0014`의 6-plane 런타임 모델은 유지 대상이며, ADR 없이 변경하지 않는다.
- 기능 추가는 이번 리팩토링의 목표가 아니다.
- 구조 개선의 성공 판정은 코드 미관이 아니라 사용자 시나리오 보존으로 한다.

### 제약

- `docs/infra/inventory/`는 공유 리소스 SoT이며, 이를 무시한 구조 개편은 금지한다.
- `docs/product/scope/`는 운영 규칙상 SoT이나 현재 루트 디렉터리 공백이 존재한다.
- FE 변경은 `web/` 전용 규칙과 시각 검증 산출물 정책을 따라야 한다.

## 3. 접근안 비교

### 접근안 A. 검증 우선 리팩토링

- 검증망을 먼저 통합한 뒤 구조를 정리한다.
- 장점: 즉시 회귀 리스크를 줄인다.
- 단점: 구조 개선 체감이 늦다.

### 접근안 B. 아키텍처 우선 리팩토링

- 책임 경계와 의존 방향을 먼저 고정한 뒤, 작은 단위로 구조를 정리한다.
- 장점: 이후 모든 변경의 판단 기준이 선다.
- 단점: 검증망이 약한 상태에서 잘못 진행하면 회귀 위험이 커진다.

### 접근안 C. 병렬 트랙 리팩토링

- 검증, BE 구조, FE 구조, 배포 체계를 동시에 병행 정리한다.
- 장점: 전체 그림을 빠르게 다룬다.
- 단점: 현재 SoT 공백과 경계 불명확 상태에서는 통제 비용이 높다.

### 선택

사용자 요청에 따라 `접근안 B. 아키텍처 우선 리팩토링`을 채택한다.
다만 실행 방식은 "큰 재작성"이 아니라 `구조를 먼저 고정하고, 이동은 작게`로 제한한다.

## 4. 목표 상태와 원칙

### 목표 상태

- `core`: 프레임워크 비의존 공통 정책과 표준 계약만 유지
- `services`: 도메인 규칙과 유스케이스의 단일 소유층
- `planes`: 런타임 조립과 transport adapter 계층
- `web`: 사용자 화면과 API 계약 소비 계층
- `deploy`/`scripts`: 운영, 생성 산출물, 검증 자동화 경계

### 원칙

1. 변경 이유가 설명되지 않는 이동은 하지 않는다.
2. 공통화보다 소유권 명확화를 우선한다.
3. 한 단계가 끝날 때마다 자동 검증 가능한 경계만 남긴다.

### 비목표

- 기능 확장
- 6-plane 모델 변경
- 도메인 병합/분할
- FE 전면 재디자인
- 무기한 중복 제거 캠페인

## 5. 목표 아키텍처와 책임 재배치 원칙

### 기준 구조

- `core`: 공통 정책, 공통 타입, 이벤트/문서/권한/설정의 표준 계약
- `services/*`: 도메인별 유스케이스, 엔티티 규칙, 저장소 인터페이스, 서비스 단위 테스트
- `planes/*`: FastAPI 앱 조립, 라우트 mount, NATS consumer 등록, scheduler wiring, gateway routing
- `web`: 화면, 폼/리스트/상세 플로우, FE 상태, API contract 소비
- `deploy`/`scripts`: 배포 렌더링, compose/helm/catalog 생성, 검증 자동화

### 금지 상태

- `core`에 도메인 정책 존재
- `services`에 plane별 런타임 분기 존재
- `planes`에 도메인 규칙 또는 중복 비즈니스 로직 존재
- `web`에 백엔드 규칙 재구현 존재
- `scripts`가 비즈니스 동작의 유일한 진입점이 되는 상태

### 재배치 원칙

1. 먼저 `경계 위반`을 분류한다.
2. 파일 이동보다 `책임 소유권 선언`을 먼저 한다.
3. 실제 변경은 `책임 이동`, `중복 제거`, `조립 코드 단순화` 세 종류만 허용한다.

## 6. 단계별 리팩토링 트랙

### 트랙 A. 아키텍처 기준선 확정

- 산출물: 책임 매트릭스, 의존 방향 규칙, 금지 의존 목록
- 목적: 이후 모든 변경의 판단 기준 마련

### 트랙 B. 런타임 조립부 정리

- 대상: `planes/*`, gateway/worker/scheduler wiring, mount 규칙
- 목적: plane에서 조립 책임만 남기기

### 트랙 C. 도메인 서비스 정리

- 대상: `services/*`
- 목적: 중복 유스케이스와 공통 문서 흐름 정리

### 트랙 D. 프론트엔드 계약 정리

- 대상: `web`
- 목적: EntityConfig, API contract 소비, 화면 조립 규칙 정렬

### 실행 순서

`A → B → C → D`

### 실행 규칙

- 트랙 A 완료 전 대규모 파일 이동 금지
- 트랙 B에서는 plane 책임 축소만 허용, 기능 변경 금지
- 트랙 C는 도메인 하나씩 vertical slice로 정리
- 트랙 D는 FE 미화가 아니라 계약 정렬 범위로 제한
- 각 트랙 종료 기준은 `경계 위반 수 감소 + 자동 검증 통과`

## 7. 검증 전략

### 계층 1. 정적 경계 검증

- 목적: 잘못된 의존 방향 조기 차단
- 수단: lint, typecheck, import 규칙, 구조 검사 스크립트

### 계층 2. 조립 검증

- 목적: 6-plane mount/wiring 유지 확인
- 수단: catalog 검증, plane boot 검증, mount smoke

### 계층 3. 데이터·배포 검증

- 목적: 마이그레이션/스키마/배포 산출물과 런타임의 정합성 확인
- 수단: migration/schema validation, deploy catalog validation, compose/helm 생성물 검증

### 계층 4. 사용자 시나리오 검증

- 목적: "부팅은 되지만 실제 흐름은 깨짐" 차단
- 수단: 핵심 백엔드 E2E + 웹 Playwright E2E
- 기준: 로그인, 핵심 CRUD, 승인/문서 흐름, 대표 cross-service 흐름 실제 수행

### 운영 목표

- 최종적으로는 `한 번의 명령`으로 위 4계층을 순서대로 실행한다.
- 내부 결과는 `경계 실패 / 조립 실패 / 데이터 실패 / 시나리오 실패`로 즉시 구분 가능해야 한다.

## 8. 성공 기준

### 트랙별 성공 기준

- 트랙 A: 책임 매트릭스와 금지 의존 규칙이 문서화되고 최소 1개 자동 검사로 강제됨
- 트랙 B: plane 코드에서 도메인 규칙이 제거되고 조립 책임만 남음
- 트랙 C: 선택한 도메인 slice에서 중복 유스케이스가 단일 소유로 수렴
- 트랙 D: FE가 contract drift를 임시 로직으로 흡수하지 않고 명시적 contract에 의존

### 전체 성공 기준

- 단일 검증 명령이 `정적 → 조립 → 데이터 → 사용자 시나리오`를 순서대로 실행한다.
- 실패 위치가 즉시 식별된다.
- 로컬, CI, 배포 전 검증 정의가 동일해진다.

## 9. 리스크와 대응

### 구조 리스크

- 책임 경계 확정 전 파일 이동이 시작되면 중복과 재분산이 재발한다.
- 대응: 책임 매트릭스와 금지 의존 규칙 선행

### 검증 리스크

- 기존 검증 자산이 많지만 운영 정의가 분산되어 있어 회귀 원인 추적이 어렵다.
- 대응: 단일 검증 명령 아래로 통합하되, 내부 결과는 계층별로 분리 출력

### 문서 SoT 리스크

- `docs/product/scope/` 루트 공백 상태로 구조 결정이 먼저 진행되면 제품 범위와 구조가 분리된다.
- 대응: 트랙 A 선행 작업으로 범위 SoT 공백 보완 포함

## 10. 실행 단위

허용 실행 단위는 세 종류만 둔다.

- 문서 단위: 책임 매트릭스, 의존 규칙, 금지 패턴 정의
- 조립 단위: 특정 plane 하나의 wiring 정리
- 도메인 단위: 서비스 하나 또는 흐름 하나의 vertical slice 정리

즉 실제 집행은 "큰 계획 1개"가 아니라, 경계 위반을 하나씩 줄이는 작은 배치들의 연속으로 수행한다.

## 11. 첫 실행 배치 권고

첫 실행 배치는 다음으로 제한한다.

1. `docs/product/scope/` 공백 보완
2. 아키텍처 책임 매트릭스 작성
3. 구조 규칙 자동검사 1개 도입

이 세 항목이 끝나기 전에는 `planes/*` 대량 정리나 `services/*` 광범위 이동을 시작하지 않는다.

## 착수 조건

다음 배치(planes 정리)는 아래 3개가 충족된 뒤에만 시작한다.

- scope SoT 공백 해소
- 구조 검사 baseline 확보
- release gate 성공
